## 1. OpenOCD MCP — ELF와 SVD를 사용한 이름 기반 검사

- **Firmware interpretation:** agent가 raw address를 임의로 해석하게 하기보다 firmware ELF symbols와 vendor CMSIS-SVD를 도구에 제공합니다.
- **Practical workflow:** 정확한 target/interface config 지정 → build한 ELF 및 SVD 연결 → 상태 읽기 → 관심 변수·register 검사 → 필요 시 제한된 flash → 결과 재조회.
- **Tools / interfaces:** OpenOCD, SWD/JTAG, ST-Link/J-Link/CMSIS-DAP, read_variable, watchpoints, SVD bitfield decode.
- **Benefits — 해석:** register와 변수 이름으로 질의하고 반복 로그 수집을 줄일 수 있습니다.
- **Limits / risks:** README의 read-only·flash/erase gate·경로/크기 제한은 프로젝트가 설명한 기능입니다. 보드 안전을 보증하지 않습니다. ELF가 실제 flash 이미지와 다르거나 SVD part/revision이 틀리면 해석도 틀릴 수 있습니다.
- **Evidence / maturity:** 공개 MCP 구현과 문서 확인 / 실험 검토 대상. 독립 현장 검증과 오늘 새 변경은 미확보.
- **Sources:** [OpenOCD MCP 구현·설정·안전 설명](https://github.com/microhenrio/openocd-mcp).

## 2. J-Link MCP — 정상 응답 대신 장치 상태를 검증하는 HIL

- **Firmware interpretation:** reset/flash/debug tool이 success를 반환해도 장치가 실제 바뀌었는지 별도의 관측으로 확인해야 합니다.
- **Practical workflow — 제안:** check_setup → snapshot → 명시적으로 승인한 build/flash → image 확인 → RTT/boot 상태 → fault injection → 기대 register/backtrace와 비교 → teardown 후 정상 boot 확인.
- **Tools / interfaces:** J-Link/GDB, snapshot, diagnose_crash, CMSIS-SVD, RTT. README는 J-Link와 OpenOCD/Black Magic backend의 성숙도를 다르게 표시합니다.
- **Benefits:** README는 실제 nRF52840-DK HIL과 golden transcripts를 이용해 “오류 없이 반환했지만 잘못된 결과”를 검출한 사례를 설명합니다.
- **Limits / risks:** reset 무효, GDB 빈 응답, RTT 중단 등은 프로젝트 작성자의 검증 보고입니다. 여기서 독립 재현하지 않았고 다른 보드·RTOS로 일반화할 수 없습니다. parse된 내용과 boot를 확인하는 test oracle이 필요합니다.
- **Evidence / maturity:** 실제 hardware test를 설명하는 프로젝트 / 독립 검증 전 참고 사례.
- **Sources:** [J-Link MCP 및 HIL 설명](https://github.com/Klievan/jlink-mcp/).

## 3. C/C++→Rust agent migration — 대규모 수치보다 승인 기준

**과거 공식 참고 사례, 새 delta 없음.** Google의 9월 30일 Argon 발표는 Fuchsia Zircon 등 C/C++→Rust migration 작업과 배포 전 자동·수동 감사 및 emulation/production 시험을 설명합니다. migration 완료나 커널 안전성이 독립 입증됐다는 뜻은 아닙니다.

- **Firmware interpretation — 제안:** port를 AI에 맡기더라도 ABI, volatile/MMIO, interrupt timing, memory layout, linker map, allocator/stack 사용을 승인 기준으로 둡니다.
- **Workflow — 제안:** 작은 순수 함수부터 port → 기존 구현과 differential test → cross-compile → size/stack/timing 검사 → 제한된 보드에서 HIL → 단계별 확대.
- **Tools / benefits:** 기존 compiler·static analyzer·simulator·board test runner로 oracle을 보강합니다. 코드 변환 속도보다 행동 동등성 확인에 초점을 둡니다.
- **Limits / maturity:** 공식 공급자 주장과 적용 제안. 대형 kernel 사례의 수치를 MCU firmware 성공률로 전환하지 않습니다. Rust 자체가 잘못된 peripheral 동작을 막는 것은 아닙니다.
- **Sources:** [Google 공식 사례](https://blog.google/innovation-and-ai/models-and-research/gemini-models/gemini-4-argon/).
