# Session 2 — AI Development Trend Radar

## 1. Agent Engineering의 중심이 “prompt”에서 “execution contract”로 이동

**What it is:** agent에게 자유롭게 일을 맡기기보다 workflow stage, tool boundary, permission, expected artifact, evaluator를 명시하는 방식이다.

**Problem it addresses:** long-running agent의 비결정성, debugging 난이도, 비용 추적, destructive action 위험을 줄인다.

**How developers are using it:** 최근 GitHub Dynamic Workflows처럼 sequential/parallel stage와 checkpoint를 코드로 정의하고, 판단이 필요한 부분만 agent에 맡기는 패턴이 대표적이다. GUI-only 도구에는 Computer Use를 사용하되 approval boundary를 둔다.

**What changed recently:** 이번 window에 완전히 새로운 대형 framework 발표가 나온 것은 아니지만, 지난 며칠의 GitHub 기능과 Gemini CLI reliability 변경이 같은 방향으로 수렴하고 있다.

**Evidence / limitations:** vendor 기능은 빠르게 늘고 있지만 independent production evidence는 아직 기능 출시 속도를 따라가지 못한다. 복잡한 orchestration 자체가 새로운 failure surface가 될 수 있다.

**Trend direction:** growing

**Maturity:** Emerging practice

## 2. Durable state와 interruption recovery가 long-running agent의 핵심 runtime 기능으로

**What it is:** context window와 별도로 task state, artifact, tool result, checkpoint를 process interruption 뒤에도 복구하는 설계다.

**Problem it addresses:** agent가 오래 일할수록 crash, cancel, network failure, extension update, context compaction 같은 운영 문제가 모델 reasoning보다 실제 성공률을 크게 떨어뜨린다.

**How developers are using it:** state persistence, checkpoint, resumable session, worktree/branch isolation, structured artifact를 사용한다.

**Evidence / limitations:** Gemini CLI main branch는 10월 3~4일에도 serialization/shared-reference와 subagent tool response 관련 수정이 활발하다. 이는 runtime이 빠르게 개선 중이라는 신호지만, open PR 자체는 stable release를 의미하지 않는다.

**Trend direction:** growing

**Maturity:** Production concern / implementations evolving

**Sources:**
- https://github.com/google-gemini/gemini-cli/pulls

## 3. Multi-model coding engine을 하나의 orchestration layer 뒤에 두는 실험 증가

**What it is:** Claude Code, Codex, Gemini CLI, Cursor Agent 같은 서로 다른 coding CLI를 공통 agent/team abstraction 뒤에 두는 방식이다.

**Problem it addresses:** 한 vendor/model에 orchestration을 고정하지 않고 task 특성이나 비용에 따라 engine을 바꾸려는 요구다.

**Evidence:** `openclaw-claude-code` 같은 community project는 Claude Code, Codex, Gemini, Cursor를 동일 team/tool layer 아래에서 실행한다. 다만 일부 engine은 persistent session이 아니라 per-message one-shot이라 context semantics가 동일하지 않다.

**Limitations:** 작은 community project 하나만으로 industry-wide adoption을 주장할 수 없다. CLI flag/output format 변경에도 취약하다.

**Trend direction:** emerging / fragmented

**Maturity:** Community experiment

**Sources:**

# Session 3 — AI for Firmware & Embedded Engineering

## 1. Cortex-M debugging이 MCP tool surface로 올라오기 시작

**Firmware interpretation:** AI coding agent가 source와 compiler output만 보는 것이 아니라 실제 target의 register, memory, RTOS task, fault register, trace/log를 tool call로 관찰한다.

**Practical workflow:** `edit → cross-compile → flash → connect probe → inspect RTOS/register/RTT → evaluate → patch → retry`.

**Useful tools / interfaces:** ProbeCodex는 OpenOCD/PyOCD/J-Link를 통해 STM32 F/G/H/L/U/WB/WL, NXP, Nuvoton 등 Cortex-M target의 GDB/FreeRTOS/flash/trace를 local MCP로 제공한다고 설명한다. `jlink-mcp`는 J-Link/OpenOCD/Black Magic backend, RTT, Cortex-M fault decode를 제공한다.

**Benefits:** agent가 hardware state를 추측하지 않고 evidence를 직접 수집할 수 있다. local execution은 proprietary firmware/symbol의 cloud exposure도 줄일 수 있다.

**Limitations / risks:** tool이 register를 읽을 수 있다고 해서 board-level correctness가 보장되지는 않는다. 잘못된 flash/memory write, option-byte 변경, peripheral drive는 실제 hardware risk를 만든다.

**Evidence / maturity:** 실제 공개 beta와 open-source implementation이 존재하지만 production adoption evidence는 아직 제한적이다. Emerging experiment.

**Sources:**
- https://www.probecodex.com/
- https://github.com/Klievan/jlink-mcp/

## 2. Agentic HIL은 raw hardware access 대신 bounded tool + evidence report를 지향

**Firmware interpretation:** agent에게 debugger shell이나 `/dev/tty*` 전체를 넘기지 않고 flash/reset/UART/CAN 같은 허용 operation만 제공한다.

**Practical workflow:** build artifact validation → policy check → flash → UART/CAN stimulus → response capture → machine-readable run report → agent evaluation.

**Benefits:** destructive operation을 policy layer에서 제한하고, test evidence를 artifact로 남길 수 있다. CI/board-farm으로 확장하기 좋은 구조다.

**Limitations / risks:** weak test oracle, non-deterministic timing, power/RF/analog measurement 부재는 여전히 남는다. 실제 안전성을 위해서는 programmable power, logic analyzer/oscilloscope, current measurement 같은 별도 instrumentation이 필요하다.

**Evidence / maturity:** Hackaday의 Agentic HIL 프로젝트는 9월 말 시작된 ongoing project로, real-board firmware loop를 목표로 한다. 아직 community experiment 수준이다.

**Sources:**
- https://hackaday.io/project/206788-agentic-hil

## 3. Firmware agent의 핵심은 Context Engineering보다 Observation + Permission Engineering

일반 software에서는 repository context가 중요하지만 firmware에서는 `ELF/DWARF + CMSIS-SVD + live probe + UART/RTT + test fixture`가 함께 있어야 한다. 동시에 operation별 permission을 나눠야 한다.

권장 기본 정책:

| Operation | Policy |
|---|---|
| ELF/SVD/source 조회 | Auto |
| register/memory read | Auto |
| UART/RTT capture | Auto |
| halt/resume/breakpoint | Scoped |
| normal flash | Restricted |
| arbitrary memory write | Confirm |
| mass erase | Explicit confirm |
| option bytes / OTP / eFuse | Explicit confirm or deny |

**Maturity:** Emerging practice.
