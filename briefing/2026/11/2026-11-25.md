# Session 3 — AI for Firmware & Embedded Engineering

이번 검색에서 신규 firmware agent 실증 사례는 충분히 확인되지 않았다. 아래는 Session 2의 사례를 기존 embedded tooling에 적용하는 설계 제안이다.

### 1. 독립적인 firmware test oracle
**Firmware interpretation / Practical workflow:** agent가 수정한 C/C++ 코드와 별도로 고정된 regression test를 실행한다. CRC 오류, frame truncation, timeout, queue overflow를 테스트하고 agent에는 실패 로그만 전달한다.

**Useful tools / interfaces:** Unity, Ceedling, clang-tidy, pytest. **Benefits:** 자기 검토 오류와 회귀 위험 감소.

**Limitations / risks:** 호스트 테스트로 ISR latency나 DMA race를 입증할 수 없다. 테스트 변경은 별도 승인 대상으로 둔다.

**Evidence / maturity:** 기존 테스트는 Production practice, agent 통합은 Experiment.

**Sources:** [Unity](https://www.throwtheswitch.org/unity) · [VentureBeat](https://venturebeat.com/technology/nearly-half-of-surveyed-engineers-and-leaders-say-the-ai-agents-that-write-their-code-also-review-it)

### 2. 병렬 simulation 및 HIL 검증
**Firmware interpretation / Practical workflow:** build artifact를 고정하고 simulator별 테스트를 병렬 실행한 뒤 실제 보드 검증은 board lock을 획득한 작업만 수행한다.

**Useful tools / interfaces:** Renode, Zephyr Twister, OpenOCD, UART capture. **Benefits:** 보드 점유 시간을 줄이고 재현 가능한 실패 로그를 확보한다.

**Limitations / risks:** simulator의 peripheral 모델 정확도, 잘못된 flash target, 전원 및 타이밍 문제. 실보드의 erase 및 option bytes 변경은 승인 대상으로 분리한다.

**Evidence / maturity:** 기존 도구 기반 설계 제안; agent 통합은 Experiment.

**Sources:** [Renode](https://renode.io/) · [Zephyr Twister](https://docs.zephyrproject.org/latest/develop/test/twister.html)

### 3. 이벤트 기반 UART 장애 분석
**Firmware interpretation / Practical workflow:** UART 수집기가 fault event를 발생시키면 agent가 ELF/map 파일과 로그를 읽고 원인 후보를 작성한다. 자동 flash나 reset은 허용하지 않는다.

**Useful tools / interfaces:** pyserial, arm-none-eabi-addr2line, CI artifact. **Benefits:** 반복적인 crash triage 시간 절감 가능.

**Limitations / risks:** 로그 내 비밀정보, 잘못된 ELF 버전, 이벤트 폭주. firmware build ID와 rate limit이 필요하다.

**Evidence / maturity:** 설계 제안, Experiment.

**Sources:** [GeekNews Pine 소개](https://news.hada.io/topic?id=37742) · [pySerial](https://pyserial.readthedocs.io/)
