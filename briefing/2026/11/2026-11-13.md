# Session 3 — AI for Firmware & Embedded Engineering

### 1. Firmware Harness Engineering
**Firmware interpretation:** agent의 변경을 실제 타깃 보드의 관측 가능한 결과까지 검증하는 반복 루프다.
**Practical workflow:** edit → cross-compile → static analysis → 승인된 flash → UART capture → HIL assertions → 실패 로그 요약 → retry.
**Useful tools / interfaces:** CMake, arm-none-eabi-gcc, OpenOCD, pyserial, pytest, J-Link/ST-LINK 및 제한된 MCP wrapper.
**Benefits:** 컴파일 성공과 실제 장치 정상 동작을 구분하고 회귀 테스트의 재현성을 높인다.
**Limitations / risks:** 잘못된 flash 주소, 보드 전원 제어, 장치 공유 경쟁, timing-dependent failure. Flash와 erase는 명시적 승인 단계로 격리한다.
**Evidence / maturity:** 기술적으로 실행 가능한 권장 설계이며 이번 기간 새 실증 사례를 확인한 것은 아니다. Emerging practice.
**Sources:** [OpenOCD](https://openocd.org/) · [pytest](https://docs.pytest.org/)

### 2. Datasheet-aware agent와 RTOS 변경 검증
**Firmware interpretation:** 레지스터 설정·interrupt priority·DMA·ThreadX/FreeRTOS 동작을 문서 기반으로 제안하고 테스트로 확인한다.
**Practical workflow:** reference manual의 정확한 장·표 인용 → 최소 patch → cross-build → unit/simulation test → 보드 테스트 → register dump 비교.
**Useful tools / interfaces:** vendor reference manual, SVD, CMSIS, clang-tidy, GDB, UART trace.
**Benefits:** HAL migration과 드라이버 리뷰에서 근거 추적이 쉬워진다.
**Limitations / risks:** 문서 revision 불일치, reserved bit 오설정, race condition, 실시간성 회귀. LLM 설명을 하드웨어 검증의 대체재로 쓰면 안 된다.
**Evidence / maturity:** 제안 workflow; 검증된 보편적 생산 사례라고 단정할 수 없다. Experiment.
**Sources:** [CMSIS](https://github.com/ARM-software/CMSIS_5) · [clang-tidy](https://clang.llvm.org/extra/clang-tidy/)
