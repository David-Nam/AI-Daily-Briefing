# Session 2 — AI Development Trend Radar

### Multi-model Harness Engineering
**What it is:** 모델과 별도로 context, tools, permissions, state, verification을 관리하는 실행 계층이다.
**Problem it addresses:** 모델을 바꿀 때마다 도구 연동과 품질 관리가 흔들리는 문제.
**How developers are using it:** 동일한 저장소 작업을 여러 모델에 할당하고, 작업 로그·테스트 결과를 공통 기준으로 평가한다.
**What changed recently:** Microsoft가 10월 말 Copilot harness의 multi-model 접근을 공식 소개했다. 이번 24시간 내 새로운 도입 효과를 입증한 독립 사례는 확인하지 못했다.
**Evidence / limitations:** 공급사 발표는 실제 생산성 개선의 독립 검증이 아니다. 격리와 평가 비용이 추가된다.
**Trend direction:** growing. **Maturity:** Emerging practice.
**Sources:** [Microsoft 공식 블로그](https://blogs.microsoft.com/blog/2026/10/28/introducing-the-microsoft-copilot-harness-unlocking-the-potential-of-truly-multi-model-agentic-work/) · [Harness Engineering 연구](https://arxiv.org/abs/2605.13357)

### Agent 실행 증거와 Eval-driven Development
**What it is:** 패치만 확인하지 않고 재현 로그, 실패 원인, 결정적 테스트, 승인 기록을 묶어 평가하는 방식이다.
**Problem it addresses:** AI가 작업을 완료했다고 주장해도 검증 가능한 증거가 부족하다.
**How developers are using it:** plan → implement → test → review 단계마다 테스트 결과와 환경 정보를 보존한다.
**What changed recently:** 새 단일 사건보다는 multi-model 도입에 따른 평가 표준화 필요성이 지속된다.
**Evidence / limitations:** Harness 연구는 통제된 검증 작업의 증거 구조를 보여주지만 광범위한 생산성 향상을 증명하지 않는다.
**Trend direction:** growing. **Maturity:** Emerging practice.
**Sources:** [Harness 연구](https://arxiv.org/abs/2605.13357) · [AI coding tools 버그 실증 연구](https://arxiv.org/abs/2603.20847)

# Session 3 — AI for Firmware & Embedded Engineering

### 1. Cross-compile 기반 Firmware Agent Harness
**Firmware interpretation:** 일반적인 coding agent의 테스트 루프를 `edit → cross-compile → static analysis → flash 승인 → UART capture → HIL assertion → retry`로 확장한다.
**Practical workflow:** MCU 타깃과 보드 리비전을 고정하고 빌드 로그를 수집한다. Flash는 명시적 승인 이후에만 수행하며 UART 출력과 전력·타이밍 검증을 결과 패키지에 첨부한다.
**Useful tools / interfaces:** CMake, arm-none-eabi-gcc, OpenOCD, pyserial, pytest, SWD/JTAG.
**Benefits:** 컴파일 오류와 재현 가능한 회귀를 자동으로 분류할 수 있다.
**Limitations / risks:** 잘못된 Flash 주소, option byte 변경, 전압 설정, 주변 장치 구동으로 장비가 손상될 수 있다. 자동 복구보다 하드웨어 보호와 승인 경계가 우선이다.
**Evidence / maturity:** 제안형 실무 워크플로(Experiment); 특정 보드에서의 성능 개선은 미검증.
**Sources:** [Harness 연구](https://arxiv.org/abs/2605.13357) · [OpenOCD](https://openocd.org/)

### 2. Datasheet-grounded RTOS 및 드라이버 검증
**Firmware interpretation:** LLM의 레지스터·인터럽트 설정 제안을 원문 매뉴얼과 타깃 SDK에 대조하는 context engineering이다.
**Practical workflow:** 레퍼런스 매뉴얼의 문서 버전과 근거 절을 명시하고, HAL 변경 전후 register map, ISR 우선순위, RTOS API 호출 제약을 자동 검사한다.
**Useful tools / interfaces:** vendor SDK, CMSIS, clang-tidy, unit test, QEMU 또는 Renode(지원 타깃에 한함).
**Benefits:** 근거 없는 register 설정과 API 환각을 조기에 발견한다.
**Limitations / risks:** 문서 검색만으로 실리콘 errata나 실제 타이밍을 검증할 수 없다.
**Evidence / maturity:** 권장 검증 패턴(Experiment); 신규 제품 기능 발표로 해석하면 안 된다.
**Sources:** [CMSIS](https://github.com/ARM-software/CMSIS_5) · [Renode](https://renode.io/)
