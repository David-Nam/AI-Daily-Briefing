# Session 2 — AI Development Trend Radar

### 1. Agent harness: 권한과 관측성을 포함한 실행 환경
**What it is / Problem:** Agent가 코드를 작성하는 것에서 끝나지 않고, tool 실행·권한 승인·결과 관찰·재시도를 통제하는 구조다.
**How developers use it:** plan → isolated edit → test → review; 실패 로그를 입력으로 다음 수정을 제한한다.
**Recent delta:** Claude Code의 11월 공개 릴리스 노트에 MCP background tasks, permission denyInsteadOfPrompting 및 자동 모드 정책 변경이 나타났다.
**Evidence / limitations:** 공식 구현은 확인되지만 범용 생산성 개선의 독립 검증은 별개다. 비동기 작업과 권한 오류는 재현성을 저하시킬 수 있다.
**Trend direction:** growing. **Maturity:** Emerging practice.
**Sources:** [Claude Code releases](https://github.com/anthropics/claude-code/releases) · [Claude Code permissions](https://code.claude.com/docs/en/permissions)

### 2. Eval-driven development와 작업 단위의 명시적 성공 조건
**What it is / Problem:** 코드 생성의 겉보기 품질 대신 실행 가능한 테스트·회귀 조건으로 결과를 평가한다.
**How developers use it:** 변경 범위와 실패 재현 테스트를 먼저 정의하고 agent가 통과 여부를 확인하게 한다.
**Recent delta:** 새 범용 벤치마크 수치보다는 agent runtime의 test feedback 및 permission 제어가 실무 점검 대상이다.
**Evidence / limitations:** 테스트가 빠진 요구사항이나 flaky test는 agent의 잘못된 성공 판정을 유발한다.
**Trend direction:** growing. **Maturity:** Production practice (일반 CI), Emerging practice (자율 수정 루프).
**Sources:** [Codex releases](https://github.com/openai/codex/releases) · [Claude Code hooks](https://code.claude.com/docs/en/hooks)

### 3. Repository context와 subagent 분업
**What it is / Problem:** 대형 저장소에서 agent가 정책과 설계를 잊거나 병렬 작업이 충돌하는 문제를 줄인다.
**How developers use it:** AGENTS.md/CLAUDE.md에 빌드·테스트·금지 작업을 적고, 작업별 branch/worktree를 격리한다.
**Recent delta:** Codex 0.171.0은 TUI에서 subagent transcript와 문서 미리보기를 제공한다고 발표했다.
**Evidence / limitations:** 컨텍스트 파일은 규칙 전달 수단이지 보안 경계가 아니다. 병렬 agent는 merge 충돌과 토큰 비용을 증가시킨다.
**Trend direction:** growing. **Maturity:** Emerging practice.
**Sources:** [Codex 0.171.0](https://github.com/openai/codex/releases) · [Claude Code docs](https://code.claude.com/docs/en/overview)

# Session 3 — AI for Firmware & Embedded Engineering

### 1. HIL harness를 펌웨어 개발에 적용
**Firmware interpretation:** edit → cross-compile → flash → UART capture → hardware assertion → retry.
**Practical workflow:** agent는 변경과 빌드까지만 자동 실행하고, flash는 지정된 테스트 보드·포트·전압 조건에서 승인 후 수행한다. UART 로그와 결과를 CI artifact로 저장한다.
**Useful tools / interfaces:** CMake, arm-none-eabi-gcc, OpenOCD, pyserial, pytest, Gitea runner.
**Benefits:** 회귀 테스트의 반복 비용과 실패 재현 시간을 줄일 수 있다.
**Limitations / risks:** 잘못된 target flash, option bytes, 전원 제어, 비결정적 타이밍, 물리적 장치 손상. 보드별 allowlist와 timeout이 필수다.
**Evidence / maturity:** 기존 임베디드 자동화 도구를 결합한 제안형 workflow; agent 자율 HIL의 보편적 성숙도는 입증되지 않았다.
**Sources:** [OpenOCD](https://openocd.org/) · [pytest](https://docs.pytest.org/)

### 2. RTOS 및 프로토콜 검증에 eval-driven 루프
**Firmware interpretation:** AI가 ThreadX/FreeRTOS 변경안을 만들되, 정적 분석·호스트 단위 테스트·실보드 검증을 분리한다.
**Practical workflow:** 메시지 프레이밍/CRC/timeout 테스트를 호스트에서 수행하고, 실제 MCU에서 queue overflow, 재연결, race condition을 검증한다.
**Useful tools / interfaces:** clang-tidy, Cppcheck, pytest, UART trace, SWD debugger.
**Benefits:** 프로토콜 edge case의 테스트 생성과 로그 분석을 빠르게 반복할 수 있다.
**Limitations / risks:** 우연히 통과한 타이밍 테스트는 동시성 안전성의 증거가 아니다.
**Evidence / maturity:** 정적 분석과 CI는 Production practice; AI가 원인을 판정하고 수정하는 루프는 Experiment.
**Sources:** [Cppcheck](https://cppcheck.sourceforge.io/) · [ThreadX](https://github.com/eclipse-threadx/threadx)

### 3. Edge AI 배포 검증
**Firmware interpretation:** 모델 최적화의 성공을 정확도뿐 아니라 latency, memory, power, thermal throttling으로 평가한다.
**Practical workflow:** 동일 입력셋을 모델 버전별로 실행하고 실제 장치의 p50/p95 latency와 오류율을 기록한다.
**Useful tools / interfaces:** ONNX Runtime, TensorFlow Lite, perf, 전력계측기.
**Benefits:** quantization 변경에 따른 성능·정확도 trade-off를 추적한다.
**Limitations / risks:** PC benchmark를 NPU/MCU 실측치로 대체할 수 없다.
**Evidence / maturity:** Production practice (측정 기반 최적화); AI agent 자동 의사결정은 Experiment.
**Sources:** [ONNX Runtime](https://onnxruntime.ai/) · [TensorFlow Lite Micro](https://github.com/tensorflow/tflite-micro)
