# Session 3 — AI for Firmware & Embedded Engineering

### 1. 검증 가능한 MCU agent harness
**Firmware interpretation:** edit → cross-compile → host test → flash 승인 → UART capture → HIL evaluation → review.
**Practical workflow:** agent는 빌드와 테스트까지만 자동 실행하고, 보드 UID·flash 주소·전원 제어는 별도 정책으로 승인한다. 테스트 결과에는 git commit, compiler version, firmware hash, board revision을 기록한다.
**Useful tools / interfaces:** CMake, arm-none-eabi-gcc, OpenOCD, pyserial, pytest, SWD.
**Benefits:** 반복적인 regression 조사와 실패 재현이 쉬워진다.
**Limitations / risks:** option bytes, bootloader 손상, 잘못된 전압 제어, flaky hardware test를 agent가 독자적으로 처리해서는 안 된다.
**Evidence / maturity:** 기술적으로 타당한 제안; 이번 기간 신규 공개된 MCU 실증 성과로 검증된 것은 아니다.
**Sources:** [OpenOCD](https://openocd.org/) · [pytest](https://docs.pytest.org/)

### 2. Protocol fuzzing과 RTOS 검증
**Firmware interpretation:** agent가 생성한 parser와 ThreadX/FreeRTOS 변경은 host-side fuzzing과 실제 보드 테스트로 독립 검증한다.
**Practical workflow:** CBOR·SLIP 입력 corpus → CRC 오류·fragmentation·timeout 테스트 → sanitizer → MCU 실행 → UART 결과 비교.
**Useful tools / interfaces:** libFuzzer, clang-tidy, AddressSanitizer, ThreadX, serial logging.
**Benefits:** 경계 조건과 예외 경로를 체계적으로 탐색할 수 있다.
**Limitations / risks:** host 테스트는 ISR priority, DMA race, timing jitter를 완전히 재현하지 못한다.
**Evidence / maturity:** 기반 도구는 성숙; AI agent 통합은 프로젝트별 검증 필요.
**Sources:** [LLVM libFuzzer](https://llvm.org/docs/LibFuzzer.html) · [Eclipse ThreadX](https://github.com/eclipse-threadx/threadx)

### 3. Edge AI 성능 평가의 독립성
**Firmware interpretation:** quantization 및 런타임 최적화는 정확도·지연시간·RAM·전력의 동일 조건 비교로 판정한다.
**Practical workflow:** 고정 입력 데이터와 버전별 모델 hash를 사용해 p50/p95 latency, peak RAM, 출력 차이를 기록한다.
**Useful tools / interfaces:** ONNX Runtime, LiteRT, perf, 전력 계측.
**Benefits:** vendor TOPS 수치와 현장 inference 성능을 구분한다.
**Limitations / risks:** thermal throttling, 데이터 분포 변화, driver 버전 차이.
**Evidence / maturity:** 평가 방법론은 Production practice; 이번 기간 신규 NPU 비교 결과는 확인되지 않았다.
**Sources:** [ONNX Runtime](https://onnxruntime.ai/docs/) · [LiteRT](https://ai.google.dev/edge/litert)
