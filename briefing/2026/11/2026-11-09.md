### 1. Harness Engineering: 모델 성능보다 실행 환경 계약
**What it is / Problem:** Coding agent의 tool loop, context 관리, 권한, sandbox, 확장 인터페이스를 일관되게 설계하는 접근이다. 동일 모델이라도 harness 차이로 재현성과 안전성이 달라진다.
**How developers use it:** AGENTS.md·CLAUDE.md·GEMINI.md, hooks, skills, MCP, 테스트 명령을 repo 단위로 관리한다.
**Recent delta:** 최근 비교 자료는 agent별 설정 계약 변화와 호환성 문제를 추적한다. 11월 7일 GitHub Copilot CLI 설정 변화도 기록됐다.
**Evidence / limitations:** 11개 coding harness를 분석한 연구는 공통 패턴을 제시하지만, 특정 패턴의 생산성 향상을 인과적으로 증명한 실험은 아니다.
**Trend direction:** growing. **Maturity:** Emerging practice.
**Sources:** [Harness 연구](https://arxiv.org/abs/2609.00006) · [DevAgentRadar](https://www.devagentradar.com/harness)

### 2. Sandboxed agent와 명시적 permission
**What it is / Problem:** Agent의 shell, network, 파일 변경, 외부 시스템 접근을 제한해 prompt injection과 과도한 실행 권한을 줄인다.
**How developers use it:** 읽기 전용 분석, 승인된 patch, 제한된 container 실행을 분리하고 tool invocation을 로깅한다.
**Recent delta:** Gemini CLI v0.67.0은 container IDE 연결, MCP 도구 메타데이터를 포함한 권한 요청, 파일 쓰기 안전성 개선을 공식 발표했다.
**Evidence / limitations:** sandbox는 권한 남용을 줄이지만 내부 테스트가 잘못된 성공 신호를 주는 문제까지 해결하지는 못한다.
**Trend direction:** growing. **Maturity:** Production practice(격리 자체), Emerging practice(agent policy).
**Sources:** [Gemini CLI changelog](https://github.com/google-gemini/gemini-cli/blob/main/docs/changelogs/latest.md)

**What it is / Problem:** 서로 다른 agent와 모델을 issue, 구현, review에 배치하는 방식이다. 단일 agent의 context 부담을 줄이는 대신 비용과 결과 병합의 복잡성이 증가한다.

# Session 3 — AI for Firmware & Embedded Engineering

### 1. Firmware Harness: compile → flash → UART → assert
**Firmware interpretation:** agent의 수정 결과를 자연어 설명이 아니라 compiler와 실제 보드의 관측값으로 판정한다.
**Practical workflow:** 변경 제안 → ARM cross-compile → static analysis → 승인된 테스트 보드 flash → UART/RTT 로그 수집 → protocol assertion → 실패 원인 분석.
**Tools / interfaces:** CMake, arm-none-eabi-gcc, OpenOCD, pyOCD, pytest, pyserial, SWD/JTAG.
**Benefits:** 반복 regression의 실행 비용을 낮추고 agent의 근거 없는 완료 선언을 줄인다.
**Limitations / risks:** 잘못된 flash 주소, option byte 변경, 전원 제어 오류, 하드웨어 편차. flash는 별도 승인 단계로 둔다.
**Evidence / maturity:** 기존 자동화 도구를 조합한 실무 설계 제안이며, agent가 실제 보드에서 자율 검증한다는 보편적 성능 증거는 부족하다.
**Sources:** [OpenOCD](https://openocd.org/) · [pyOCD](https://pyocd.io/) · [Harness 연구](https://arxiv.org/abs/2609.00006)

### 2. STM32WBA ThreadX BLE CoC 테스트의 agent 적용
**Firmware interpretation:** agent가 BLE CoC throughput 문제를 수정할 때 RX/TX thread scheduling, buffer exhaustion, disconnect 처리의 정량적 oracle을 사용한다.
**Practical workflow:** 고정 payload와 connection parameter → 반복 전송 → throughput·loss·latency 수집 → thread trace 비교 → patch 검토.
**Tools / interfaces:** ThreadX trace, ST-LINK, BLE test peer, Python 로그 파서.
**Benefits:** 재현이 어려운 성능 저하를 측정 가능한 회귀 테스트로 전환한다.
**Limitations / risks:** RF 간섭, 연결 파라미터 차이, 타이밍 비결정성. 단일 run 성공을 합격으로 간주하지 않는다.
**Evidence / maturity:** 적용 제안(Experiment); 공개된 특정 STM32WBA agent 실증 사례를 이번 조사에서 확인하지 못했다.
**Sources:** [Eclipse ThreadX](https://github.com/eclipse-threadx/threadx) · [ST STM32WBA](https://www.st.com/en/microcontrollers-microprocessors/stm32wba-series.html)

### 3. PSCP protocol fuzzing과 경계 분리
**Firmware interpretation:** CBOR·SLIP·CRC16-XMODEM 파서를 host에서 먼저 fuzz하고, 장치에서는 승인된 안전 입력만 replay한다.
**Practical workflow:** malformed frame 생성 → host parser property test → 정상·오류 ACK/NACK 검증 → 제한된 실장비 회귀.
**Tools / interfaces:** pytest, Hypothesis, libFuzzer, USB-NCM, TCP capture.
**Benefits:** 장치 flash 없이도 파서 경계 조건과 세션 상태 오류를 발견할 수 있다.
**Limitations / risks:** host 모의 환경은 MCU 메모리·동시성 문제를 완전히 재현하지 못한다.
**Evidence / maturity:** 기존 fuzzing 기술에 기반한 실무 설계 제안(Emerging practice).
**Sources:** [Hypothesis](https://hypothesis.readthedocs.io/) · [LLVM libFuzzer](https://llvm.org/docs/LibFuzzer.html)
