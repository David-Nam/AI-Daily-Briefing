# Session 2 — AI Development Trend Radar

### 1. Harness Engineering의 평가 대상 확대
**What it is:** Coding agent를 모델뿐 아니라 실행 loop, tool, context, memory, 권한 정책을 포함한 시스템으로 다루는 접근이다.
**Problem / usage:** 긴 작업에서 tool 실패와 context 손실을 줄이기 위해 harness 구성요소를 개별적으로 측정하고 수정한다.
**Recent delta:** 최근 연구들은 harness 구성과 관찰 가능성이 성능에 미치는 영향을 실험했으며, 단일 prompt 최적화보다 실행환경 설계를 강조한다.
**Evidence / limitations:** 논문 실험의 benchmark 개선이 모든 실제 repository에 재현된다고 볼 수는 없다.
**Trend direction:** Growing. **Maturity:** Emerging practice.
**Sources:** [Harness source-code study](https://arxiv.org/abs/2609.00006) · [Agentic Harness Engineering](https://arxiv.org/abs/2604.25850)

### 2. Agent permission과 공급망 보안
**What it is:** Skills, hooks, MCP server 및 allow-rule을 코드 의존성처럼 관리하는 방식이다.
**Problem / usage:** 무심코 승인한 광범위 권한이나 악성 repository 지시문이 agent를 우회 실행시킬 수 있다.
**Recent delta:** 2026년 연구에서는 agent 설정의 공급망 결함과 승인 규칙 확대 공격을 실증했다.
**Evidence / limitations:** 실험 성공률을 전체 사용자 환경의 침해율로 일반화해서는 안 된다.
**Trend direction:** Growing / challenged. **Maturity:** Emerging production practice.
**Sources:** [Supply-chain configurations study](https://arxiv.org/abs/2609.07360) · [Privilege escalation study](https://arxiv.org/abs/2610.22987)

### 3. Multi-agent orchestration과 비용 대비 성능
**What it is:** 서로 다른 agent에 계획, 구현, 테스트, 리뷰를 분담하고 결과를 통합하는 구조다.

# Session 3 — AI for Firmware & Embedded Engineering

### 1. 검증 가능한 Firmware agent harness
**Firmware interpretation:** edit → cross-compile → 정적 분석 → flash 승인 → UART capture → HIL test → evaluate → retry.
**Practical workflow:** agent는 소스 수정과 빌드까지 자동 수행하되 보드 erase/flash는 허용된 장치 ID와 이미지 hash를 확인한 후 실행한다.
**Useful tools / interfaces:** CMake, arm-none-eabi-gcc, OpenOCD, pyserial, pytest, GitHub Actions.
**Benefits:** 컴파일 오류와 회귀 테스트를 빠르게 반복하고 실패 로그를 축적할 수 있다.
**Limitations / risks:** 전원 상태, 보드 revision, 실시간 타이밍과 장비 손상 위험 때문에 완전 무인 실행은 부적절할 수 있다.
**Evidence / maturity:** 일반 harness 연구를 펌웨어에 적용한 기술적 제안이며 해당 구성의 현장 성능은 검증되지 않았다.
**Sources:** [Harness architecture study](https://arxiv.org/abs/2609.00006) · [OpenOCD](https://openocd.org/)

### 2. RTOS·드라이버 변경의 test-feedback loop
**Firmware interpretation:** LLM이 HAL/RTOS 변경안을 작성하고 build, unit test, serial log, stack/heap 계측으로 평가한다.
**Practical workflow:** 변경 전후 task priority, interrupt latency, stack watermark와 protocol timeout을 비교한다.
**Useful tools / interfaces:** CMock/Unity, pytest, GDB, SEGGER RTT, logic analyzer.
**Benefits:** 반복적인 driver migration 및 로그 분석을 보조한다.
**Limitations / risks:** 성공한 빌드만으로 race condition이나 하드웨어 타이밍 안전성을 입증할 수 없다.
**Evidence / maturity:** 기술적으로 실현 가능한 workflow 제안; 범용 실증 자료는 제한적이다.
**Sources:** [Unity test framework](https://github.com/ThrowTheSwitch/Unity) · [Zephyr testing](https://docs.zephyrproject.org/latest/develop/test/index.html)

### 3. Firmware용 MCP/agent 권한 경계
**Firmware interpretation:** 디버거, flash tool, serial console을 agent에게 제공하되 읽기와 쓰기 권한을 구분한다.
**Practical workflow:** register read와 로그 수집은 자동 허용하고 mass erase, option bytes, bootloader 변경은 수동 승인한다.
**Useful tools / interfaces:** MCP tool wrapper, OpenOCD, J-Link Commander, udev device allowlist.
**Benefits:** agent의 실제 장비 접근을 감사 가능한 interface로 제한한다.
**Limitations / risks:** 넓은 allow-rule은 승인 이후에도 지속되는 보안 위험을 만들 수 있다.
**Evidence / maturity:** 보안 연구를 embedded 장비 제어에 적용한 설계 제안이다.
**Sources:** [Privilege escalation study](https://arxiv.org/abs/2610.22987) · [MCP specification](https://modelcontextprotocol.io/specification/)
