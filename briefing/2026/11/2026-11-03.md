# Session 3 — AI for Firmware & Embedded Engineering

### 1. 제한된 Hardware-in-the-Loop Agent
**Firmware interpretation:** 코드 작성 성공이 아니라 실제 보드 동작을 완료 조건으로 삼는다. **Workflow:** edit → cross-compile → artifact 검사 → 승인된 flash/reset → UART/CAN 측정 → 기대값 비교 → 재시도. **Tools:** Agentic HIL의 MCP, ST-Link/OpenOCD, pyserial, pytest. **Benefits:** 컴파일 성공과 동작 성공을 구분하고 로그를 재현 가능한 증거로 남긴다. **Risks:** 잘못된 flash, 전원·핀 설정, 시험 장치 공유 충돌. 장치·명령 allowlist와 전원 차단 장치가 필요하다. **Evidence / maturity:** 공개 프로젝트와 STM32 Nucleo 예제는 존재하지만 대규모 산업 현장 검증은 확인되지 않은 Experiment. **Sources:** [Agentic HIL](https://github.com/agentic-hil/agentic-hil) · [Nucleo-F446RE 실습](https://hackaday.io/project/206788-agentic-hil)

### 2. SWD/RTT 기반 Crash Diagnosis를 Agent Tool로 분리
**Firmware interpretation:** Agent에게 GDB shell 전체를 주기보다 레지스터 읽기, HardFault 해석, RTT 로그 수집 같은 좁은 도구를 제공한다. **Workflow:** fault 발생 → PC/LR/CFSR/HFSR 및 stack 수집 → ELF symbolication → 원인 가설 → 재현 테스트. **Tools:** jlink-mcp, SEGGER J-Link, OpenOCD, arm-none-eabi-gdb. **Benefits:** 반복적인 원인 분석 시간을 줄이고 증거를 구조화한다. **Risks:** 메모리 읽기의 비밀정보 노출, halt에 따른 실시간 동작 교란, 디버거 연결 시 전기적 위험. **Evidence / maturity:** nRF52840-DK 실기기 데모가 있는 Community experiment. **Sources:** [jlink-mcp](https://github.com/Klievan/jlink-mcp)

### 3. STM32WBA·ThreadX·PS-Link에 적용할 실무 Harness
**Firmware interpretation:** BLE CoC와 PSCP 같은 상태 기반 프로토콜은 Agent가 생성한 코드보다 deterministic test가 중요하다. **Workflow:** host-side frame/CRC/SLIP unit test → cross-build → 보드별 smoke test → UART 및 TCP trace 수집 → ACK/NACK·timeout·재연결 판정. **Tools:** pytest, Python socket/serial, ThreadX 진단 로그, 제한된 flash 스크립트, GitHub Actions/self-hosted runner. **Benefits:** 프로토콜 회귀를 자동 검출하고 재현 로그를 남긴다. **Risks:** RF 환경 변동, 타이밍 민감성, 실장비 동시 접근, destructive flash. **Evidence / maturity:** 검증된 상용 사례가 아니라 위 HIL 도구를 기존 프로젝트에 적용하는 **제안 설계**다. **Sources:** [GitHub Agentic Workflows](https://github.blog/changelog/2026-10-28-github-agentic-workflows-generally-available/) · [Agentic HIL](https://github.com/agentic-hil/agentic-hil)
