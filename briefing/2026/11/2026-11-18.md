# Session 3 — AI for Firmware & Embedded Engineering

### 1. Hardware-in-the-loop harness

**Firmware interpretation:** AI가 코드를 수정한 뒤 실제 보드에서 통과 조건을 확인하는 실행 루프다.

**Practical workflow:** edit → cross-compile → firmware hash 기록 → 대상 보드 확인 및 flash 승인 → UART/SWD 로그 캡처 → pytest/HIL 평가 → 실패 원인 요약 및 retry.

**Useful tools / interfaces:** arm-none-eabi-gcc, CMake, OpenOCD, pyOCD, pyserial, pytest, Zephyr Twister.

**Benefits:** 컴파일 성공과 실제 기능·타이밍 성공을 분리해 검증한다.

**Limitations / risks:** 잘못된 flash 대상, option bytes, 전원·핀 손상, 불안정한 테스트 fixture, 장비 공유 경쟁. Flash는 승인·보드 식별·복구 경로를 갖춰야 한다.

**Evidence / maturity:** Zephyr Twister의 보드 테스트 기반은 공식 문서화되어 있으나 AI agent와의 자동 통합은 개별 구현 검증이 필요하다.

**Sources:** [Zephyr Twister](https://github.com/zephyrproject-rtos/zephyr/blob/main/doc/develop/twister/index.rst)

### 2. RTOS·BLE·UART 프로토콜을 위한 eval-driven 수정

**Firmware interpretation:** Agent의 목표를 단순 빌드가 아닌 frame 정합성, 재연결, queue exhaustion, timeout 등으로 정의한다.

**Practical workflow:** CBOR/SLIP/CRC16-XMODEM golden vector → malformed frame fuzzing → ThreadX queue stress → BLE reconnect → UART trace와 firmware commit 보존.

**Useful tools / interfaces:** pytest, Hypothesis, clang-tidy, host AddressSanitizer, SWD debugger, logic analyzer.

**Benefits:** agent가 놓치기 쉬운 오류 처리와 race condition을 반복 검사할 수 있다.

**Limitations / risks:** 호스트 sanitizer는 ISR/DMA와 MCU 타이밍을 재현하지 못하며, 하드웨어 테스트에는 재현 seed와 전원 초기화가 필요하다.

**Evidence / maturity:** 기존 테스트 도구는 성숙했으나 자율 수정·재flash의 안전성은 별도 실증이 필요하다.

**Sources:** [Hypothesis](https://hypothesis.readthedocs.io/) · [Zephyr Twister](https://github.com/zephyrproject-rtos/zephyr/blob/main/doc/develop/twister/index.rst)
