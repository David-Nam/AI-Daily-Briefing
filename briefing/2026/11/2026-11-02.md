- **What / problem:** coding agent의 extension, skills, hooks, MCP server는 개발자 권한으로 실행될 수 있다. 허가되지 않은 명령이나 악성 패키지를 프롬프트만으로 막을 수 없다.
- **How / recent delta:** Cursor 사고는 공식 이름으로 보이는 배포물도 저장소와 배포 경로별로 검증해야 함을 보여줬다. 실제 운영에서는 버전 pinning, artifact hash, 최소 권한, SSH·credential 접근 모니터링을 결합한다.
- **Evidence / limitations:** Cursor·Microsoft·Phorion의 일치하는 사고 분석은 강한 근거다. 모든 IDE marketplace가 동일하게 침해됐다는 뜻은 아니다.
- **Direction / maturity:** Growing / Production security practice.
- **Sources:** [Cursor 공지](https://cursor.com/blog/claude-code-extension-security-notice) · [Microsoft 분석](https://www.microsoft.com/en-us/security/blog/2026/10/30/inside-malicious-claude-code-branded-cursor-extension-persistent-ssh-backdoor/)

- **What / problem:** agent가 코드를 빠르게 만들수록 '테스트 통과'가 요구사항의 올바름까지 보장하지 못하는 문제가 커진다.

- **Evidence / limitations:** 증명은 명세가 맞다는 가정 아래에서만 유효하다. AI가 만든 형식 모델이 원래 구현과 동등한지 검증해야 하며 모든 시스템에 적용하기에는 비용이 크다.
- **Direction / maturity:** Growing / Emerging practice, 검증 도구 자체는 성숙.
- **Sources:** [Leo de Moura 인터뷰](https://thedataexchange.media/leo-de-moura-lean-aws/) · [Lean](https://lean-lang.org/)

### 3. Multi-agent orchestration의 benchmark와 재현성 논쟁
- **What / problem:** 작은 모델 여러 개의 독립 해답을 결합하면 단일 큰 모델보다 비용 대비 결과가 좋을 수 있지만, 검증 설정이 결과를 좌우한다.
- **How / recent delta:** Memdoor 프로젝트는 Qwen3.8-27B 다섯 개를 조합해 LiveCodeBench Hard의 선택된 10문제에서 높은 결과를 얻었다고 주장했다. 요청·응답·grader 기록을 공개했고 10월 31일 Hacker News에서 논의됐다.
- **Evidence / limitations:** 선택된 10문제와 제한된 반복은 전체 benchmark의 우위를 증명하지 않는다. 모델 호출 수, token, wall-clock latency, 실패율까지 동일 조건으로 비교해야 한다.
- **Direction / maturity:** Growing but challenged / Experiment.
- **Sources:** [Memdoor 저장소](https://github.com/guregodevo/memdoor) · [Hacker News](https://news.ycombinator.com/front?day=2026-10-31)

### 4. Agentic workflow의 상태 보존·검증 gate
- **What / problem:** 장기 작업은 agent가 '완료'라고 말하는 것보다 재시작 가능 상태, 산출물 검사, 승인 gate가 중요하다.
- **How / recent delta:** Memdoor는 YAML workflow, 병렬 step, 검사 명령과 중단 지점 재개를 제공한다. Cursor의 10월 Agent SDK 역시 instructions/tools/channels/evals를 코드로 정의해 배포하도록 한다.
- **Evidence / limitations:** 도구의 기능 공개는 확인되지만 서로 다른 조직의 생산성 향상이나 비용 절감은 별도 실험이 필요하다. 에이전트에게 검사 결과를 자기 평가하게 하는 것은 위험하다.

# Session 3 — AI for Firmware & Embedded Engineering

### 1. Simantic: firmware simulator를 AI agent의 test oracle로 사용
- **Firmware interpretation:** coding agent의 edit → build → run → evaluate loop를 실제 MCU를 기다리지 않는 virtual devboard로 확장한다.
- **Practical workflow:** STM32용 빌드를 생성하고 가상 보드에 적재한 뒤 UART·GPIO·주변장치 동작을 API로 검증한다. 통과한 변경만 실제 보드 HIL로 승격한다.
- **Useful tools / interfaces:** Simantic cloud simulator, firmware review bot, GitHub CI, Renode/QEMU(대조군).
- **Benefits:** 초기 보드 부재, 반복 flash 시간, agent 검증 대기시간을 줄일 잠재력이 있다.
- **Limitations / risks:** 업체는 STM32F0/F4/H7, ESP32-S3/C3, RP2040 일부 모델 지원을 주장한다. 개발자는 mixed-signal 및 외부 보드 회로는 별도 모델링이 필요하다고 인정했다. timing fidelity, peripheral coverage, 비용은 직접 검증해야 한다.
- **Evidence / maturity:** 창업팀 공개 데모와 HN Q&A; 독립 검증 부족 / Emerging product.
- **Sources:** [Simantic Launch HN](https://news.ycombinator.com/item?id=50291116) · [Simantic](https://simantic.com/cloud-sim) · [Renode](https://github.com/renode/renode)

### 2. RTOS·BLE용 Harness Engineering: simulation과 실제 보드의 이중 gate
- **Firmware interpretation:** ThreadX, BLE CoC, DMA·interrupt 코드는 코드 리뷰보다 시간·상태 전이·자원 사용량 검증이 중요하다.
- **Practical workflow:** `edit → host unit test → cross-compile → simulated boot → 보드 예약 → SWD flash → UART/trace 수집 → timeout·stack·reconnect assert → review`로 분리한다. 파괴적 flash, option byte 변경, 전원 제어는 별도 승인 gate에 둔다.
- **Useful tools / interfaces:** CMake/CTest, Unity/Ceedling, clang-tidy, pyserial, OpenOCD, labgrid, SWD, ThreadX trace.
- **Benefits:** AI의 잘못된 HAL 호출, buffer overflow, reconnect 회귀를 재현 가능한 증거로 검출한다.
- **Limitations / risks:** simulator는 아날로그 특성·실제 전원·RF 환경을 대체하지 못한다. 테스트 oracle이 부정확하면 자동화가 잘못된 성공을 반복한다.
- **Evidence / maturity:** 도구별 사용은 성숙; agent를 닫힌 루프로 연결한 전체 workflow는 제안 / Experiment.
- **Sources:** [Simantic HN 토론](https://news.ycombinator.com/item?id=50291116) · [labgrid](https://github.com/labgrid-project/labgrid)

### 3. Protocol state machine의 AI-assisted formal verification
- **Firmware interpretation:** BLE 연결 상태, SLIP/CBOR frame parser, CRC 처리, retransmission의 불변식을 먼저 명세하고 AI가 반례를 찾도록 한다.
- **Practical workflow:** `length bounds`, `CRC fail → reject`, `disconnect → resources released`, `duplicate ACK → no duplicate side effect` 등을 property로 정의한다. host fuzzing과 property-based test를 우선하고, 안전성이 중요한 핵심 상태 전이는 TLA+/Lean 등으로 작은 모델을 검증한다.
- **Useful tools / interfaces:** libFuzzer/AFL++, Hypothesis, TLA+, Lean, sanitizer, UART packet replay.
- **Benefits:** 컴파일만으로 드러나지 않는 상태 전이·경계 조건 결함을 줄일 수 있다.
- **Limitations / risks:** 명세 자체가 틀리거나 실제 RTOS scheduling을 모델이 생략하면 증명이 실제 보드를 보장하지 않는다.
- **Evidence / maturity:** formal method 자체는 기존 기술; AI와의 결합은 Emerging practice.
- **Sources:** [Leo de Moura 인터뷰](https://thedataexchange.media/leo-de-moura-lean-aws/) · [Lean](https://lean-lang.org/)
