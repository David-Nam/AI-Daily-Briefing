# Session 2 — AI Development Trend Radar

### 1. Permission-aware agent harness
**What it is / Problem:** Agent의 shell·파일·네트워크 실행을 정책과 검증 루프로 제한해 무인 실행의 위험을 줄이는 접근이다.
**How developers use it:** 작업별 권한, 독립 worktree, 테스트 명령, 실패 로그, human approval을 명시한다.
**What changed recently:** Claude Code 2.1.319 릴리스는 gateway 환경의 auto mode 판단, MCP background tasks, 제한된 세션의 파일 접근 등 여러 동작을 수정했다. 이번 24시간 내 새 변경이라는 뜻은 아니다.
**Evidence / limitations:** 공식 릴리스는 구현 근거이지만 전체 사용자 환경의 신뢰성 증거는 아니다. 권한 완화는 공급망 및 destructive command 위험을 높인다.
**Trend direction:** growing. **Maturity:** Emerging practice.
**Sources:** [Claude Code releases](https://github.com/anthropics/claude-code/releases) · [Permission docs](https://code.claude.com/docs/en/permission-modes)

### 2. Context engineering과 repository instructions
**What it is / Problem:** 장기 세션에서 작업 규칙과 근거 문서를 재현 가능하게 제공해 context drift를 줄인다.
**How developers use it:** CLAUDE.md/AGENTS.md에 build, test, architecture boundaries와 금지 동작을 간결하게 기록한다.
**What changed recently:** 11월 초 공개된 실무 가이드는 hooks, subagents, permissions와 함께 설정 예제를 정리한다. 새로운 표준이 확정됐다는 근거는 아니다.
**Evidence / limitations:** 사례 가이드는 유용하지만 통제 실험이 아니며, 긴 지침은 비용과 충돌을 늘릴 수 있다.
**Trend direction:** growing. **Maturity:** Emerging practice.
**Sources:** [Practitioner guide](https://github.com/luongnv89/claude-howto) · [Claude Code docs](https://code.claude.com/docs/en/overview)

### 3. Eval-driven agent workflow
**What it is / Problem:** 코드 작성 완료 여부 대신 독립 테스트와 실제 동작으로 성공을 판정한다.
**How developers use it:** plan → implement → test → review, 실패 유형별 재시도, 변경 diff 검토를 결합한다.
**What changed recently:** 이번 검색 기간에 채택률을 정량화할 만한 새 자료는 확인하지 못했다.
**Evidence / limitations:** 단위 테스트 통과가 요구사항 충족을 보장하지 않고, LLM-as-a-judge는 평가 편향을 가진다.
**Trend direction:** stabilizing. **Maturity:** Production practice (일부 구성 요소), 전체 자율 루프는 Emerging practice.
**Sources:** [Claude Code hooks](https://code.claude.com/docs/en/hooks) · [GitHub Actions](https://docs.github.com/en/actions)

# Session 3 — AI for Firmware & Embedded Engineering

### 1. Hardware-aware harness
**Firmware interpretation:** edit → cross-compile → static analysis → flash 승인 → UART capture → HIL test → 평가 → retry.
**Practical workflow:** 개발자는 테스트 보드와 flash 대상 UID를 고정하고 agent에는 우선 build/test만 허용한다. 실제 flash와 전원 제어는 별도 승인 단계로 분리한다.
**Useful tools / interfaces:** CMake, arm-none-eabi-gcc, OpenOCD, pyserial, pytest, GitHub Actions.
**Benefits:** 재현 가능한 오류 로그와 회귀 검증.
**Limitations / risks:** 잘못된 flash 주소, option bytes, 전압/전류 제어, 물리적 타이밍 변동.
**Evidence / maturity:** 기술적으로 실행 가능한 설계 제안; 특정 상용 팀의 신규 도입 사례로 확인된 것은 아니다.
**Sources:** [OpenOCD](https://openocd.org/) · [pytest](https://docs.pytest.org/)

### 2. RTOS 및 protocol agent 검증
**Firmware interpretation:** AI가 ThreadX/FreeRTOS task, queue, ISR 또는 CBOR/SLIP parser 변경을 제안하더라도 결과는 deterministic test로 판정한다.
**Practical workflow:** host-side parser fuzzing → cross-build → race/timeout 시나리오 → 보드 UART 로그 비교.
**Useful tools / interfaces:** clang-tidy, AddressSanitizer(host), libFuzzer, pytest, SWD/UART.
**Benefits:** edge case 발견과 반복 테스트 자동화.
**Limitations / risks:** host sanitizer는 MCU memory ordering, ISR latency, DMA 동작을 그대로 재현하지 못한다.
**Evidence / maturity:** 기존 검증 도구를 agent에 연결하는 실무 설계; 신규 AI 도입 효과 수치는 미확인.
**Sources:** [LLVM libFuzzer](https://llvm.org/docs/LibFuzzer.html) · [ThreadX](https://github.com/eclipse-threadx/threadx)

### 3. Edge AI 배포 검증
**Firmware interpretation:** 모델 정확도와 별도로 메모리 사용량, 지연시간, 소비전력, thermal throttling을 측정한다.
**Practical workflow:** 동일 입력 데이터셋을 quantization 전후로 실행하고 p50/p95 latency, peak RAM, 출력 차이를 기록한다.
**Useful tools / interfaces:** ONNX Runtime, TFLite, perf, 전력 계측기.
**Benefits:** 칩·런타임 최적화의 실제 효과 분리.
**Limitations / risks:** benchmark 환경과 현장 입력 분포 차이, vendor benchmark 편향.
**Evidence / maturity:** 검증 방법론은 성숙; 최근 24시간의 새 성능 발표는 확인되지 않았다.
**Sources:** [ONNX Runtime](https://onnxruntime.ai/docs/) · [LiteRT](https://ai.google.dev/edge/litert)
