# Session 3 — AI for Firmware & Embedded Engineering

### 1. Firmware harness: edit → cross-compile → flash → UART → evaluate
**Firmware interpretation:** Agent의 성공 조건을 코드 생성이 아니라 실제 보드에서의 재현 가능한 통과 기준으로 정의한다.

**Practical workflow:** STM32 프로젝트에서 `cmake --build` 또는 `west build` 실행 → artifact와 firmware hash 기록 → 승인된 보드에만 flash → UART 로그 수집 → timeout·assert·전력·프로토콜 결과 평가 → 실패 시 코드 수정. Flash 단계는 기본적으로 인간 승인 필요.

**Useful tools / interfaces:** CMake, arm-none-eabi-gcc, OpenOCD, pyOCD, pyserial, pytest, Zephyr Twister.

**Benefits:** 컴파일 성공과 실제 동작 성공을 구분하고 회귀를 빠르게 찾는다.

**Limitations / risks:** 잘못된 flash 대상, option byte 변경, 전원/핀 손상, 보드 상태의 비결정성. 테스트 장비 예약·복구·전원 차단 기능이 필요하다.

**Evidence / maturity:** Zephyr Twister의 실제 보드·fixture·multi-DUT harness는 공식 문서화된 production-grade 테스트 기반이다. 여기에 AI agent를 연결하는 것은 설계 제안이며 검증된 완제품 사례라는 뜻은 아니다.

**Sources:** [Zephyr Twister documentation](https://github.com/zephyrproject-rtos/zephyr/blob/main/doc/develop/twister/index.rst)

### 2. BLE/RTOS protocol agent의 검증 경계
**Firmware interpretation:** AI가 ThreadX queue, BLE CoC, UART framing 코드를 수정하더라도 기능 테스트 외에 메모리·타이밍·연결 해제 동작을 확인해야 한다.

**Practical workflow:** CBOR/SLIP/CRC16-XMODEM에 대해 golden vectors, malformed frame fuzzing, ACK/NACK retry, reconnect, queue exhaustion, race condition을 테스트한다. 테스트 실패의 재현 seed와 firmware commit을 보존한다.

**Useful tools / interfaces:** pytest, hypothesis, clang-tidy, AddressSanitizer(호스트 테스트), SWD debugger, UART capture.

**Benefits:** Agent가 놓치기 쉬운 경계 조건을 자동 검증한다.

**Limitations / risks:** 호스트 sanitizer는 MCU ISR·DMA·실시간 타이밍을 재현하지 못한다. 실제 보드 HIL과 병행해야 한다.

**Evidence / maturity:** 도구와 테스트 방법은 성숙했으나 해당 조합의 agent 자율 수정은 실험 단계다.

**Sources:** [Hypothesis](https://hypothesis.readthedocs.io/) · [Zephyr Twister](https://github.com/zephyrproject-rtos/zephyr/blob/main/doc/develop/twister/index.rst)
